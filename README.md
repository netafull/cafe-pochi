# カフェポチ

スターバックス・タリーズ・コメダ珈琲店・ドトールコーヒーショップの**季節限定・新作メニュー**を1日1回巡回して記録し、
販売が終わって公式サイトから消えても記録が残るアーカイブにするサイト（公開予定 https://cafe.netaful.jp/ ）。
価格・カロリーなどの栄養成分・アレルゲン・掲載期間を、あとから引ける形で残す。

姉妹サイト [電書ポチ](https://book.netaful.jp/)・[家電ポチ](https://kaden.netaful.jp/)・
[林檎ポチ](https://apple.netaful.jp/)・[漫画ポチ](https://manga.netaful.jp/)・
[コンビニポチ](https://conbini.netaful.jp/)・[ファストフードポチ](https://fastfood.netaful.jp/)と同じく、
pip依存なしのPython標準ライブラリだけ（HTML解析は正規表現、PDFは扱わない）。
**構造は `fastfood-pochi` の汎用エンジン**（保存スキーマ・終了判定・歯止め・価格履歴・run_summary/_health・通知・サイト生成・RSS・
sitemap・広告枠のJS・ネタフル記事のひも付け）を引き継ぎ、チェーン固有の取得だけを4社分に作り直している。
サイトの色は茶系 `#6D4C41`（ダークモードは `#BCAAA4`）。広告(AdSense)とGA4は config の値が空の間は何も出力しない
（`adsense_client_id` / `adsense_ad_slot` / `ga_measurement_id` は**最初は空**。広告の仕組み＝ヘッダー下1枠＋カード一覧に12件おき最大3枠＋商品ページ1枠は
ファストフードポチと同じで、値を入れれば有効になる）。

## 使い方

```bash
python3 scripts/crawl.py                    # 全チェーンを巡回して data/products/ に蓄積
python3 scripts/crawl.py komeda             # チェーンを指定すると、そのチェーンだけ巡回する
python3 scripts/fetch_netaful_reviews.py    # ネタフルの記事を取得・商品とひも付け
python3 scripts/generate_site.py            # docs/ 一式を生成
python3 -m unittest discover -s tests       # 合成フィクスチャでテスト(公式データのコピーは使わない)
```

定期実行は `.github/workflows/update.yml`（workflow_dispatchのみ。scheduleもpushトリガーも無い）を Cloud Scheduler から起動する前提
（ジョブ名の案 `cafe-pochi-update`、毎朝1回）。通知の `NTFY_TOPIC` は GitHub Secrets（コードに書かない・最初は未設定＝通知なし）。
一時停止は リポジトリ変数 `NTFY_PAUSED=true`。**開発中は本番サイトを必要最小限しか叩かない。**

## 規約上の方針（最重要）

**4社とも規約が複製・転載・引用を禁じているため、記録・表示するのは事実だけ。**

- 保存・表示する: 商品名・価格（税込）・サイズ別価格・発売日/掲載日・記録開始日・終了（観測）日・カロリーなどの栄養成分・アレルゲン・
  公式ページへのリンク（とあればプレスリリース／お知らせへのリンク）。
- **保存も表示もしない: 説明文（冒頭の引用も含む）・画像・画像URL。** パーサは説明文・画像のキーを読み取りもしない
  （`image_url` `photo_url` `description` `lead` 等は保存データのどこにも入らない。テストで確認している）。
  プレスリリース・お知らせの本文は**発売日と商品名の照合のためにメモリ上で読むだけで、保存しない**。
- 各商品ページに「出典：○○公式サイト（取得日）」と公式ページ・プレスリリースへのリンクを付ける。サイトのaboutに
  「記録しているのは事実情報だけで、説明文・画像は載せていない。詳しくは各社公式へ」と書いてある。
- 取得は**素のUA**（`CafePochi/1.0 (+https://cafe.netaful.jp/)`。ブラウザ偽装はしない）。リクエスト間隔は2秒（コードの下限は1秒）、
  チェーンごとに1回の実行の上限（`max_requests_per_run`: スターバックス50・タリーズ40・コメダ40・ドトール60）。
  ブロック（403/429・チャレンジページ）されたら**回避せず**そのチェーンを止めて `blocked` に記録する。robots.txt は各ホストで1回取り、Disallowは守る
  （robots.txt が404や、HTMLを返すサイトは全許可。Python標準の robotparser は `*` のワイルドカードを解釈しない）。

## 何を記録するか

- **初回から、その時点で季節限定・新作として載っている商品を全部記録する**（ファストフードポチの「既存品は記録しない baseline 方式」ではない）。
  `data/baseline_ids.json` は「初回に見えた記録対象のID」を持ち、**2回目以降の歯止めの判定にだけ使う**。
- 商品1件1ファイル `data/products/{starbucks|tullys|komeda|doutor}/{id}.json`。既存ファイルは丸ごと上書きしない（初回取得が正）。
  更新するのは last_seen_at / status / price_history 等の追跡項目と、まだ空の栄養成分・アレルゲン・発売日だけ。
  公式の栄養値が後から変わったら入れ替えて `nutrition_changes` に残す。
- 画像・説明文は保存しない（上記）。

### 販売状況の追跡（サイトの核）

- 巡回で一覧に居たら `last_seen_at` を更新し `status=on_sale`。価格（と価格の上限）が前回と違えば `price_history` に追記。
- **そのチェーンの一覧取得が全部成功した回だけ**、一覧から消えた商品を数える。一覧のどれか1ページでも取得失敗・0件（構造変更の疑い）・
  robots.txtでDisallow・歯止めの保留の回は数えない。
- **別の日に連続2回**見つからなかったら `status=ended`、`ended_observed_at` にその日付。同じ日に何度実行しても1回と数える（`last_miss_date`）。
- 終了後に再登場したら `on_sale` に戻し、`relaunches` に記録、昨季の期間を `seasons` に残し、今季の発売日は未確定に戻す
  （昨季の日付を今季として出さない）。再登場時の価格を `price_history`（`relaunch: true`）に足す。
- **終了日は公式発表の最終販売日ではなく「公式の一覧から消えたことを確認した日」**。サイト上にもそう書いている。一覧から外れただけで
  店頭ではまだ売っていることもある（特にタリーズの「季節の新商品」は新商品の枠を外れただけの可能性）。
- **歯止め（burst guard）**: 新規候補（baselineにも既存レコードにも無い項目）が `max(new_burst_min_by_chain, 一覧の項目数×new_burst_ratio(0.6))` を超えたら、
  公式のID体系・ページ構造の変更とみなして、その回はそのチェーンの新規を記録せず終了判定もしない（保留。`pending.json` の `_suspected_restructure`、
  `run_summary.json` の `suspected`）。3日連続の保留で通知が「要判断」に変わる。**初回（baselineが無い）は対象外。**
  閾値はスターバックス20・タリーズ6・コメダ8・ドトール5が下限（ホリデーの入れ替えで一度に10品ほど新作が出ても保留しないよう、ファストフードポチより高め。
  全件が新規になるID体系の変更は全社で検知できる）。
- **記録対象の急減の検知**（`data/list_state.json`）: 記録対象が前回の半分未満（前回8件以上のとき）に減ったら、**3日続くまで**終了判定をしない
  （取得の不具合の疑い。季節の入れ替えで本当に減ったなら3日目に受け入れる）。
- `data/run_summary.json`（gitに入れない）と `pending.json` の `_health` で、ブロック・一覧の失敗・例外・連続日数を `notify.py`（ntfy）に伝える
  （ファストフードポチと同じ仕組み。詳細ページ単発の失敗は翌日自動で再試行されるので通知しない）。

### 発売日の拾い方（共通）

`find_launch`: プレスリリース・お知らせの**見出し**に商品名（正規化して5文字以上。末尾の（単品）・先頭の【店舗限定】を除く）があり、
同じ見出しの「11月2日（月）より」「〜より発売」の日付を発売日にする。見出しに名前が無く**本文**にだけ名前がある記事は、
商品名の近く（60文字以内）の日付→無ければ本文の最初の発売日を使い、`launch_date_source` に `_body` を付けて区別する
（商品ページにも「複数の商品をまとめた記事のため、商品ごとの発売日とずれることがあります」と出す）。
記事の日付が商品の初観測日（またはタリーズの掲載日）の前120日〜後14日のものだけ対象。「12月25日まで」のような終わりの日付は拾わない。
**他の商品のより長い名前に含まれるだけの出現は数えない**（「ジョイフルメドレー ティー」が「…ティー ラテ」の記事に誤って結びつかないように）。
拾えなければ `launch_date: null` で、サイトには「記録開始日」（タリーズは「公式サイト掲載日」）から表示し、発売日ではないと明記する。

## 取得元

### スターバックス (menu.starbucks.co.jp / product.starbucks.co.jp / stories.starbucks.co.jp)

- 新作一覧 `https://menu.starbucks.co.jp/api/v1/list?tag=new&start=N`（JSON、10件ずつ。2026-11-03は count=129で13リクエスト）。グッズ・豆・ギフトも含み、
  期間限定を示す項目は無い。`count` に届くまで取り、届かない・途中のページが取れない回は「一覧が不完全」として終了判定をしない。
- **記録対象**: (a) 新作一覧にあって、栄養JSON（`https://product.starbucks.co.jp/allergy/json/nutritions.json`、約1MB）にもある商品
  ＝飲食物（グッズ・豆は栄養JSONに無いので入らない）、(b) 栄養JSONの STARBUCKS「季節のおすすめ」(c01)にあって(a)に入らなかった商品
  （新作一覧に載っていないホット/アイスの片方など。名前のホット/アイス表記を除いて新作一覧に同名があれば価格を借り、無ければ価格なし。
  `is_menu_product=false` で価格も分からないものは入れない）。`limited_kind` は c01 なら「季節のおすすめ」、そうでなければ「新作」。
  商品IDは13桁の `item_code`（= 栄養JSONの `url_jan_code`）。リザーブ・ロースタリー東京の商品も、新作一覧にあって栄養JSONにあれば記録する
  （`stores_note` に販売チャネル。一部店舗のみは明記）。
- 栄養JSONが読めない回は、記録対象を決められないので何も記録せず `list_failed`。アレルゲンJSON（`allergens.json`）だけ取れない回は記録を続け、次回以降に埋める。
- **栄養は標準のサイズ別**: `nutrition_by_milk` のミルクは `no_change`（ミルク変更なし）を標準とし、無ければ（ミルクを使わない商品）`_milk_type: null`、それも無ければ `milk`。
  ミルク変更・カスタマイズは載せず公式へ案内する。代表は Tall（無ければ先頭。フードは STANDARD）、`nutrition_variants` にサイズ別。
  アレルゲンも同じ行（標準のミルク）で、公式のアレルゲンページの表示名（卵・乳・小麦…魚介類。まつたけは公式が非表示）。
- 公式の商品ページは `https://menu.starbucks.co.jp/{item_code}`（SPA。本文は読まない）。
- 発売日: プレスリリースRSS `https://stories.starbucks.co.jp/press/press-releases/feed/`（最新10件）の見出し・概要で照合し、
  見つからなければ見出しに発売日の語がある記事の**本文を最大10本**（`starbucks_article_fetch_max`）取って照合（その回のメモリ上だけ。
  発売日が未確定の商品は最大3回の巡回まで探す）。`www.starbucks.co.jp` は一時503になるので使わない。
- 価格は新作一覧の `price_in_vat_min`〜`max`（税込。サイズ・店内/持ち帰りで異なるので範囲で表示）。
- リクエスト: robots×3 + 一覧13 + 栄養JSON + アレルゲンJSON + RSS1 + 記事本文（最大10）＝ 通常日は約20、初回は約27。
- 2026-11-03の初回: 27リクエスト・36件記録（季節のおすすめ 26＋新作 10。ビバレッジ26・フード10。通常店舗13・ロースタリー8・リザーブ カフェ7・ティー&カフェ4ほか）、栄養36/36・アレルゲン36/36・発売日12/36（うち本文由来10）。

### タリーズコーヒー (www.tullys.co.jp)

- 一覧 `https://www.tullys.co.jp/menu/seasonal_lineup/`（静的HTML。`<li class="… js_item_list_new" data-new="2026-10-07 11:09:12">`）。2026-11-03は9件。
- **記録するのはドリンク・フード・スイーツ**（`tullys_record_prefixes`: `/menu/drink/` `/menu/food/` `/menu/sweets/`）。**コーヒー豆（/menu/beans/）・グッズ・
  ハニー/グロッサリーは記録しない**（栄養が無く、スターバックスの豆・グッズと同じ扱い）。除外した名前は `stats.skipped_non_food` に残る。
- 商品IDは詳細URLのパス（`/menu/drink/coffee/26x.html` → `drink-coffee-26x`）。年の接頭辞（26）が付くslugは翌年変わりうるので、同じ商品でも別IDの別レコードになる（既知）。
- `data-new` は公式の掲載日時なので `listed_at`（公式サイト掲載日）として保存・表示する（発売日ではない）。
- 詳細（新規・7日ごとの取り直し・1回の実行で最大6件）: 価格はサイズ別（Short/Tall/Grande。税込。店内・テイクアウト同一価格の表記）、
  エネルギーはHOT/COLD×サイズのkcalだけ（公式が公表しているのはkcalのみ）、アレルゲンは「商品に含まれる特定原材料 8品目」のアイコン。
  **アレルゲン欄はあるが品目の表示が無い商品（エアロカーノ）は `none_listed` として「公式ページに表示された品目はありません」と出す**（「含まない」とは断定しない）。欄自体が無ければ null。
  詳細が404・失敗でも商品は記録し（`first_seen_at` を失わない）、次回に埋める。
- 発売日: `https://www.tullys.co.jp/company/pressrelease/{年}_index.html` の見出し（「10月7日より」「9月28日（月）より期間限定発売」）で商品名照合（年は実行日から。1〜2月は前年も）。
- robots.txt は `User-Agent: Googlebot` だけの実質全許可。旧商品ページは消える（404）。
- リクエスト: robots + 一覧 + 詳細（新規のみ）+ プレス1。初回11リクエスト・8件記録、栄養8/8・アレルゲン8/8・発売日1/8。

### コメダ珈琲店 (eu.komeda.co.jp / www.komeda.co.jp)

- 一覧は公開JSON `https://eu.komeda.co.jp/v1/hp/menu?brand_type=1&category=903`（おすすめ。2026-11-03は10件、全件 `is_limited_time: true`）。
  **レスポンスは dict `{"constant": {...}, "menus": [...]}`**（2026-11-03に確認）。内部APIなので、**構造が変わったら（list だけ・menus が無い・id/name が無い項目）
  「構造変更の疑い」として list_failed 扱いにし、終了判定をしない。** `is_hidden` は記録しない。`limited_kind` は限定なら「季節限定」、そうでなければ「おすすめ」。
- 商品IDは数値ID。価格は文字列範囲（`national_price_eatin: "680～740円"`）→ 最小〜最大。店舗で異なる旨を表示。
- 栄養・アレルゲン `https://eu.komeda.co.jp/v1/hp/menu-allergy/{id}`（商品ごと1回。`calori`（kcalのみ公表）と `menu_allergies[{name,is_allergy}]`）。
  **取得済みの商品は毎日取り直さず、新規時と7日ごと（1回の実行で最大6件）に再確認。** `allergy_comment` は公式の注記なので短ければ注記として出す。
- 発売日: お知らせJSON `https://eu.komeda.co.jp/v1/hp/notice?limit=20&type=2&offset=0`（本文付きで1リクエスト）の見出し・本文の「10月28日（水）より」を商品名照合。
- 公式の商品リンクは一覧ページ `https://www.komeda.co.jp/menu/?brand=1`（SPAで商品個別URLが無い）。robots.txt は404。
- 初回: 13リクエスト・10件記録、栄養10/10・アレルゲン10/10・発売日9/10（全て本文由来）。

### ドトールコーヒーショップ (www.doutor.co.jp / allergy.doutor.co.jp)

- 季節のおすすめ `https://www.doutor.co.jp/dcs/menu/season.html`（静的HTML）。`<div id="menuN" class="dcs-season-product">` の中の
  `<li class="dcs-season-menuList-item">` が1商品。名前は `dcs-season-menuList-name`、価格は `pprice eatin-price`（「¥570～」。サイズ列は `size_str`）か
  `__head`（価格/販売価格/宅配価格）+`__body`。**価格の無い項目（「■店頭受取」「■宅配」「■ドトール バリューカードキャンペーン」「今年は…ピック付！」）は商品ではないので除外。**
  クリスマスケーキの「予約承り期間・お渡し期間」は `reservation` として保存・表示し、お渡し期間を「終了予定」に使う。
  **価格のラベルに「コーヒー豆」「ドリップ」「パック入」を含む商品（豆・ドリップ）は記録しない**（`doutor_goods_words`。2026-11-03はプレミアムマイルドブレンド）。
  ページに1つもブロックが無ければ構造変更の疑い（list_failed）。
- カテゴリ一覧 `/dcs/menu/list/{hotdrink,icedrink,milano,hotdog,hotsandwich,toast,morning,sweets}.html`（8ページ）のカードから14桁の商品ID（詳細URLのパス）と
  NEW印（`new_icon`）を取る。季節のおすすめの商品名とカードを、表記揺れ（全角半角・空白・波ダッシュ、「～…～」の副題）を正規化して照合し、一致すればそのIDを使う。
  **一致しない（クリスマスケーキなどの予約品）は名前から作るID `sx-…`**（以前に名前で作ったIDがあれば、あとでカードと一致してもそのIDを使い続ける）。
  NEW印のカードで季節のおすすめに載っていないものは「新商品（NEW）」として記録（価格は詳細ページ `rt_cf_price_eat_in`。HTMLコメント内は読まない）。
- **終了判定は「季節のおすすめにも、8つのカテゴリ一覧のどれにも無い」とき**（どちらかに居れば販売中）。8ページが全部成功した回だけ。
  ※定番の「ミルクレープ」のように季節のおすすめのページに並んで載る定番品は、そのページに載っている間だけでなくカテゴリ一覧に居る限り終了しない。
- 栄養・アレルゲン: `https://allergy.doutor.co.jp/allergy_check/doutor_coffee_shop/search/?menu_category=2-1-`（ドリンク）`2-2-`（フード）`2-3-`（デザート）の一覧
  （`<a href="…/item/detail/11003073" class="cards_item">`）と商品名で、同名（またはアイス/ホットの接頭辞つき）の商品だけ詳細を取る。
  **一覧3ページは、栄養・アレルゲンが未取得の商品がある日（新規・7日ごとの再確認）にだけ取る。** エネルギー・たんぱく質・脂質・炭水化物・食塩相当量は**1食当たり**。
  サイズ違いは `infoTab` のボタン名がラベル。
- **アレルゲンの凡例（実装前に確認済み）**: 29カードの `infoCards_item-circle`＝「●」含む、`-triangle`＝「△」（のり・しらすのえび・かに、二枚貝のかにの混入に由来する条件つきの表示）、
  `-line`＝含まない。確認元は、アレルギーサイトのCSS（`.infoCards_item-circle .infoCards_iconArea:before{content:"●"}` ほか）と、詳細ページの注意書き

## 既知の限界

- **終了＝一覧からの消失**。公式の最終販売日ではなく、一覧の枠から外れただけのこともある。スターバックスは「新作一覧（tag=new）」から外れた・「季節のおすすめ」から外れた、
  タリーズは「季節の新商品」から外れた、ドトールは季節のおすすめとカテゴリ一覧の両方から消えた、で判定する。
- スターバックスは「飲食物か」の判定を栄養JSONの有無に頼っているので、新作一覧にあっても栄養JSONに無い飲食物は記録しない（2026-11-03時点: パネトーネ2種・ロースタリーのカクテル（ストロベリー フィズ No.68 の別バージョン・ティバーナ スプリッツァー）・スパイス アップル サイダーなど）。
  栄養JSONに載ったら次回から記録される。ホット/アイスで栄養JSONの項目が別の商品は別レコードになる（例: 「ジンジャーブレッド ラテ」と「…（アイス）」）。
- スターバックスの新作一覧の価格は最小〜最大の範囲で、サイズ別の価格は取れない。栄養のミルク変更・カスタマイズは載せない。
- タリーズは年の接頭辞つきslug（`26_…`）の商品が翌年に別IDになる。コメダは価格が店舗ごとに違い、範囲でしか載せられない。
- ドトールは発売日の一次情報が無い。クリスマスケーキなどの予約品はアレルギーサイトに載っておらず、栄養・アレルゲンは公式リンクでの案内になる。
  季節のおすすめのページには定番品（ミルクレープなど）も並ぶので、定番が「季節限定」として記録されることがある（終了判定はカテゴリ一覧にも居る間は止まる）。
- 発売日はプレスリリース・お知らせの見出し/本文から拾えたものだけ（スターバックス12/36・タリーズ1/8・コメダ9/10・ドトール0/6。本文由来は複数商品の記事なのでずれることがある）。
- 4社とも内部API・SPA・HTML構造の変更に弱い。壊れたら list_failed/保留として通知される（終了判定はしない）。
- スターバックスの `www.starbucks.co.jp` は一時503（メンテナンス）になるので使っていない。
